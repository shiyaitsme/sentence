# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`sentence · 摘抄本` — a personal excerpt/commonplace-book app. Record text passages with source, free-form tags, and personal notes; search and filter by tag. Frontend is Vite + React, data lives in Cloudflare D1, deployed as a single Cloudflare Pages project (static site + API in one).

## Commands

```bash
npm install
npm run dev:full          # full stack: Pages Functions + local D1, via wrangler — use this, not `npm run dev`
npm run db:local:init     # one-time: create local D1 tables from d1/schema.sql
npm run db:local:migrate  # one-off: apply d1/migrations/0001_add_author.sql to a local DB created before the author column existed
npm run build             # vite build → dist/
npm run lint              # oxlint
```

`npm run dev` (plain Vite) only serves the frontend — `/api/*` calls will fail because the Functions layer and D1 binding don't exist outside wrangler. Always use `npm run dev:full` when working on anything that touches data.

There is no test suite in this repo.

## Architecture

**Two-layer app, one deployment.** The React app never talks to a database client directly (unlike a typical Supabase/Firebase setup) — it calls a small REST API over `fetch`, and that API is Cloudflare Pages Functions backed by D1 (SQLite). Both the static frontend and the Functions live in the same Cloudflare Pages project and deploy together on every push.

```
src/hooks/useExcerpts.js  --fetch-->  functions/api/excerpts/index.js   (GET list, POST create)
                                      functions/api/excerpts/[id].js    (PUT update, DELETE)
                                            |
                                            v
                                      env.DB  (D1 binding, see wrangler.toml)
```

- `functions/_utils.js` holds the shared bits both route files import: `parseTags` (splits a free-text tag string on commas/spaces into a deduped array), `toExcerptRow`/`fromDbRow` (convert between the API's `{tags: string[]}` shape and D1's `tags` column, which is a JSON-encoded string — D1/SQLite has no array type), and `jsonResponse`.
- Route files are Cloudflare Pages Functions file-based routing: `functions/api/excerpts/index.js` → `/api/excerpts`, `functions/api/excerpts/[id].js` → `/api/excerpts/:id`. Handlers are named exports per HTTP verb (`onRequestGet`, `onRequestPost`, `onRequestPut`, `onRequestDelete`), each receiving `{ request, env, params }`. `env.DB` is the D1 binding declared in `wrangler.toml` (binding name must stay `DB` — the Functions code and the Cloudflare Pages dashboard binding both hard-code that name).
- IDs are generated with `crypto.randomUUID()` inside the POST handler (not by D1/SQLite itself). Timestamps are ISO strings generated in JS, not SQLite's `CURRENT_TIMESTAMP`.
- There is no auth layer. Anyone who can reach the deployed URL can hit the CRUD endpoints — acceptable for a single-user notebook, called out explicitly in the README. If auth is ever added, it needs to live in the Functions layer (e.g. a `functions/_middleware.js`), since that's the only place requests are intercepted server-side.

**Frontend data flow**: `src/hooks/useExcerpts.js` is the only thing that calls the API; it owns the `excerpts` list state and exposes `addExcerpt`/`updateExcerpt`/`deleteExcerpt`/`refetch`. `src/App.jsx` owns UI-only state (search text, which of the three views is active, which excerpt is being edited/viewed) and derives `tagCounts` and the filtered list with `useMemo` — filtering/search is entirely client-side over the full fetched list, there's no server-side query filtering. There's no router: `App.jsx` holds a `view` string (`'home' | 'list' | 'record'`) and renders one page component accordingly; `NavBar` just calls back into that state setter.

**Tag filter state**: tag filtering is split into two independent facets — `selectedCountryTags` and `selectedTopicTags` — plus a third, non-tag facet `selectedAuthors`, and `openFilterGroup` (`'country' | 'topic' | 'author' | null`) tracking which one is expanded (the three facets expand exclusively; selections within each are independent of the others). `src/lib/tagGroups.js` classifies each tag from `tagCounts` into a facet via `splitTagGroups` — there's no DB field distinguishing a "country/period" tag from a plain topic tag (see D1 schema below), so classification is a static curated keyword list (`COUNTRY_PERIOD_TAGS`); anything not in that list falls into the topic facet by default. The author facet is different: it reads `excerpt.author` directly (a real column, not a tag) rather than going through `tagGroups.js`, and `App.jsx` derives its `authorCounts` the same way it derives `tagCounts` but keyed on the single `author` string instead of the `tags` array. Filtering ANDs every selected tag across both tag facets against `excerpt.tags`, then separately ANDs against the author facet with `selectedAuthors.includes(excerpt.author)` (OR-within-facet, since one excerpt has exactly one author) — the multi-facet split is presentation only for the tag facets, but the author facet is a genuinely different match against a different field.

**D1 schema** (`d1/schema.sql`): single `excerpts` table — `content`, `source`, `author`, `tags` (JSON text column, see above), `note`, `created_at`/`updated_at` — indexed on `created_at`. `author` is a plain nullable text column, populated only from the "作者" field on `RecordPage` (never derived from tags or parsed out of `source`). Local dev D1 state lives in `.wrangler/` (gitignored) — `npm run db:local:init` seeds it from the same schema file used in production. Databases created before the `author` column existed need the one-off migration in `d1/migrations/0001_add_author.sql` (`npm run db:local:migrate` locally; see README for remote).

**Deployment**: Cloudflare Pages project name is `sentence`, connected to this GitHub repo with automatic deploys. The D1 binding (`DB` → `sentence-db`) is configured on the Pages project itself (dashboard: Settings → Functions → D1 database bindings), not something `wrangler.toml` pushes on deploy — `wrangler.toml` is only consulted for local `wrangler` commands (`dev:full`, `db:local:init`). If the production/preview D1 binding is ever lost or needs recreating, `wrangler.toml`'s `database_id` is the value to re-bind with.

## App structure: three views, no router

The app has three views switched by local state in `App.jsx` (`view: 'home' | 'list' | 'record'`), not a router:

- **`HomePage`** (`'home'`, the default) — full-viewport-height (`min-height: max(600px, 100vh)`, so it always fills the first screen with no leftover blank strip below it) hero band using `public/landing_page.png` as a cover photo with a dark gradient overlay, a centered headline + two CTAs, and a "今日一句" footer strip showing the most recent excerpt plus live counts (excerpts / distinct sources / distinct tags). Hero content is wrapped in `.hero-content` (max-width 1400px, centered) and key type sizes use `clamp()` rather than fixed px — both exist because the design was authored on an ~860px canvas, and without them the hero looks disproportionately small and the background photo crops far more aggressively on wide/ultra-wide viewports.
- **`ExcerptListPage`** (`'list'`) — "摘抄集": title + "+ 新建摘抄", a three-level filter bar, and a CSS `columns`-based waterfall of `ExcerptCard`s. The filter bar is a "全部" pill plus three expandable facet triggers — "国家 / 时期", "作者", "标签" (see Tag filter state above) — only one expands at a time, clicking a trigger reveals its facet's chips (`.filter-subchip`) below the row; a search box sits at the row's right edge. Clicking a card opens `ExcerptDetail` as a modal (view/edit/delete).
- **`RecordPage`** (`'record'`) — "记录": the create/edit form (content, source, author, note, a removable tag-chip editor with a "+ 添加标签" input, and a decorative image dropzone that only previews client-side via `FileReader` — there's no image upload/storage in the backend, so nothing here is persisted to D1). The "作者" field is a plain text input distinct from "出处" (source) — it's the field the list page's "作者" filter facet reads from, entered once here rather than added as a tag. The "个人感想 / 批注" textarea (`.autosize`) auto-grows to fit its content via a `ref` + `useEffect` that sets `style.height` to `scrollHeight` on every change, instead of a fixed row count. Layout is a CSS grid (`.record-body`, two columns: fields ~1.4fr / upload 220px) rather than flex, specifically so the upload dropzone's height and top edge can be pinned to the content/note textareas — `align-items: stretch` (grid default) makes `.upload-box` grow to match the fields column's total height, and a `margin-top` on `.record-upload` (equal to the "原文内容" label's line-height + field gap) nudges its top down to line up with the textarea below the label rather than the label itself. The tags field, the "AI 提取 Prompt" pill, and the action row each get their own grid row (`.record-tags-field` / `.record-prompt-row` / `.record-bottom-actions`) so the pill can be bottom-aligned with "+ 添加标签" and right-aligned under the upload box via `grid-row`/`justify-content`, independent of the actions row below. The "AI 提取 Prompt" pill opens `AiPromptModal` — a prompt template for asking an AI to extract a photographed excerpt into this app's field format (原文内容/出处/作者/个人感想/标签), with one-click copy and an edit mode. The prompt text is stored client-side in `localStorage` (`sentence:ai-prompt`), never sent to D1 — same "personal, per-device, no backend" pattern as the image preview above it.

`NavBar` (used by all three, with `variant="overlay"` on the photo and `variant="plain"` on the cream background) is the only navigation affordance; `App.jsx`'s `handleNavigate` clears any in-progress edit whenever you navigate to `'record'` from the nav so it opens a blank form, while `startEdit` (called from card/detail edit buttons) sets the target excerpt first.

## Visual design system

The UI follows a warm ink-and-blush palette (not monochrome): deep navy for text/buttons, a blush/terracotta accent for tags and highlights, cream/ivory cards on a warm gray page background. The hero photo (`public/landing_page.png`) is the only place a busy image sits directly behind content; the list and record pages are flat-colored.

- `src/index.css` is the single stylesheet (no CSS modules/CSS-in-JS). Color tokens are CSS custom properties in `:root`: `--navy` (#2a3b4d, primary text/buttons), `--navy-mid`, `--slate` (#8fa7bb, secondary text), `--blush` (#eab9b3, accent/selected state), `--terracotta` (#b3776f, quote marks/danger), `--card` (#faf5ee, opaque card fill), `--bg` (#f3ede6, page background), `--cream` (#f6ece2, text-on-photo). Retheme by changing these, not per-rule.
- Fonts, loaded via Google Fonts `@import` at the top of `index.css`: `Bodoni Moda` for Latin display type (logo, stat numbers), `Noto Serif SC` for Chinese headings and excerpt body text, `Noto Sans SC` for UI copy, `Oswald` for uppercase nav/button/eyebrow labels, `Petit Formal Script` for the one handwritten accent line on the hero. Font stacks put the Latin display font first and `'Noto Serif SC'`/`'Noto Sans SC'` as fallback so Chinese characters in a Bodoni Moda/Oswald-labeled string don't fall back to a mismatched system font.
- No picture-frame/corner-ornament chrome anymore — cards (`.wf-card`, `.modal-card`) are plain rounded rectangles (`border-radius: 14–16px`) with a soft shadow, no border.
- Reusable pill/chip patterns: `.filter-pill` (the list page's "全部" pill, `.active` = blush fill), `.filter-group-trigger` (the "国家 / 时期" / "标签" facet triggers, `.open` = solid navy fill while expanded — tracks expand state only, not whether the facet has selections), `.filter-subchip` (chips inside an expanded facet, `.selected` = light slate-blue fill/border, `rgba(143,167,187,.28)` bg + `--slate` border + `--navy` text), `.card-tag` (waterfall card footer category tag, `--accent`/`--neutral` color variants picked deterministically per tag via a hash in `ExcerptCard.jsx`), `.tag-chip` (record page's removable tag editor). `.filter-pill` and `.filter-group-trigger` are both fixed at `height: 36px` with `box-sizing: border-box` and share the same `Oswald` 11.5px / `letter-spacing: .06em` styling (as does `.filter-search`, also 36px) so the whole filter row lines up regardless of label length — don't let one drift to a different font-size/padding than the others. Don't reuse one chip class for another context — the selected/unselected color rules differ slightly per spec.
- The hero band (`.hero-page`/`.hero-inner`) is the only place `nav-row--overlay` (light text, text-shadow, translucent borders) is used; every other view uses `nav-row--plain` and normal dark-on-light text since their background is the flat `--bg` cream, not a photo.

## PWA (iOS-focused)

The app is installable to an iOS home screen, but there's no build-time PWA tooling (no Workbox/vite-plugin-pwa) — everything is hand-written and lives in `public/` so Vite copies it to `dist/` unchanged:

- `public/manifest.json` — name/`display: standalone`/theme colors, deliberately has no `icons` array (iOS doesn't need it; kept minimal rather than as a deliberate anti-shadow measure — see below).
- What actually drives the iOS experience is in `index.html`: `<link rel="apple-touch-icon">` (three sizes: 180/167/152) and the `apple-mobile-web-app-capable` / `apple-mobile-web-app-status-bar-style` / `apple-mobile-web-app-title` meta tags. Users install via Safari's share sheet → "添加到主屏幕" (no auto-prompt). iOS caches the home-screen icon at add-time and never re-fetches it for an already-installed icon — if you change the art, existing installs need to be deleted and re-added; the `?v=` query params on both the favicon and the apple-touch-icon links exist so at least fresh adds/tab loads don't serve a stale cached response.
- **Icons must be fully opaque with no alpha channel at all — don't key/cut out the background.** An earlier version of `sentence_logo_v4.png` had its white background keyed out to transparency (inverted-greyscale-as-alpha trick) and recomposited onto the `--card` cream color; on-device this rendered as a washed-out, shadowed/blurred icon both in the Safari tab and on the home screen, even though the generated files individually inspected as byte-correct. Root cause looked exactly like iOS/Safari treating *any* icon carrying transparency (even a fully-opaque-everywhere alpha channel) as eligible for some adaptive/shadowed rendering path — a working sibling project confirmed the fix by comparison: it never removes the source image's original background at all, just resizes the as-uploaded flat image. `public/icons/icon-*.png` (and the favicon `public/sentence_logo_v5.png` itself) are now plain resizes of the original upload — `sharp(src).resize(size).flatten({background:'#fff'}).removeAlpha().png()` — keeping its native white background untouched, matching that working precedent. If a future logo upload needs to sit on the brand's cream background instead of white, flatten onto `--card` (#faf5ee) at generation time — just never leave an alpha channel in the output, and view the result directly at its production URL (not just locally) before assuming it's fixed, since a "correct" file and a "correct-looking icon" turned out to be two different questions here.
- Even with a byte-correct opaque icon, iOS's home-screen renderer still overlays a system-wide glass/lighting effect (bright top, darker/faded bottom) on every icon, native or web. It's most visible on marks that are one large continuous solid shape (the v3/v4 geometric marks) and far less noticeable on marks with a lot of internal linework breaking up the fill (the current handwritten-script mark, similar to why a detailed icon like an app mascot doesn't show it) — there's no manifest/link-tag setting that disables this for web-clip icons, so if it resurfaces, it's a source-art density issue, not a config bug.
- `public/sw.js` is a minimal hand-written service worker (network-first, falls back to cache when offline) registered from `src/main.jsx` on `window.load`. It explicitly skips caching anything under `/api/` — excerpt data is dynamic and there's no auth, so a stale cached API response would be actively misleading. There's no precache list keyed to Vite's hashed build filenames (that's what tools like Workbox are for); it only caches what's actually been fetched at runtime.
- The viewport meta tag in `index.html` is `width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no`, and `html`/`body` also set `touch-action: pan-x pan-y` in `index.css`. Both exist to make the home-screen app always open filling the screen at 1:1 scale instead of whatever zoom level Safari last remembered, and to suppress pinch/double-tap zoom generally. Neither is a complete fix on iOS: Safari has ignored `user-scalable=no` for pinch-zoom since iOS 10 (an intentional accessibility override that no page can bypass) — `touch-action` is a second layer that some browsers still honor even when they ignore the viewport meta, not a guarantee of fully blocking zoom on iOS.
